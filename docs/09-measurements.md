# 測定結果

複数台の実機で N 体計算(粒子 65,536 個)を動かし、1 ステップにかかる時間を測りました。結論から書くと、1 ステップの中央値は **4,850 ms から約 370〜410 ms** に縮みました。この章では、何をどう測り、何が効き、何が効かなかったかを順に説明します。

## 結果の要約

| 段階 | 1 ステップ(中央値) | 主な変更 |
|---|---|---|
| 出発点 | 4,850 ms | 共有入力(全粒子の位置)を、タスクごとに送っていた |
| 共有入力と SIMD カーネル | 約 1,765 ms | 位置を 1 ノードにつき 1 回だけ送る。力の計算を 8 粒子ずつまとめ、WASM の `simd128` を使う |
| 配り方とスケジューラの改善 | 約 570〜750 ms | 位置データの圧縮と先送り、速いノードからの転送、速さに応じた割り当て、状態保存の間引き |
| ネイティブカーネル(AVX2) | 約 450 ms | 計算を WASM でなく、ワーカー内蔵の AVX2 カーネルで行う |
| 自動チューニングと `ForgetJob` | **約 370〜410 ms** | ブロック数の自動選択、結果の往復時間を含めた割り当て、終わったジョブの削除 |

目標にした「700 ms 台」は、WASM のままでも多くの回で達成できました。ネイティブカーネルと自動チューニングで、さらにその半分ほどになっています。

## 測定の条件

### 計算の中身

- 全粒子の組み合わせ(all-pairs)で重力を計算します。1 ステップで 65,536 × 65,536 ≒ 43 億回の相互作用を計算します。
- 全粒子の位置は 65,536 × 24 バイト ≒ 1.5 MB です。これを「共有入力」として各ワーカーに 1 回だけ送り、タスクごとには担当する粒子の範囲(開始番号と終了番号)だけを送ります。
- 結果は、1 スレッドで計算した値とビット単位で一致するように作ってあります(足し算の順序を固定し、FMA を使いません)。

### 使った機械

サーバーは kuro(手元のマシン)で動かしました。ワーカーは次の機械です。

| 名前 | 貸したコア数 | 特徴 |
|---|---|---|
| gyh | 3 | 4 コア・メモリ 3 GB。AVX2 なし。サーバーへの回線が遅い(約 1.4 MB/s) |
| wasat | 16 | Core i9-10980XE(18 コア)。サーバーへの回線が遅い(約 1.4 MB/s) |
| anna | 32 | 36 コア・メモリ 251 GB。他の利用者も使っている。サーバーへの回線は最も速い(約 10 MB/s) |
| procyon | 16 | ssh の踏み台(triton)経由。サーバーへ UDP が届かないので、後述のトンネルで接続 |

kuro・gyh・wasat・anna は tailscale でつないであります。wasat と anna の間は、測った時点では tailscale の中継(DERP)を通っていました。

### 測り方

- `examples/nbody_batch.rs` を使います。各ステップの経過時間(ms)を並べて出し、中央値を使います。
- 平均ではなく中央値を使うのは、ときどき 1 秒を超えるステップが混ざるためです。
- 1 回の測定は 10〜60 ステップです。

## 何が効いたか

### 1. 位置データを 1 回だけ送る(共有入力)

タスクごとに 1.5 MB の位置データを付けると、通信が計算より重くなります。位置データはサーバーに 1 回登録し、各ワーカーが 1 回だけ受け取ります。タスクには範囲だけが残るので、通信量は桁違いに減りました。

### 2. 力の計算を速くする(SIMD カーネル)

8 粒子ずつまとめて計算し、WASM の `simd128` 命令を使うと、1 コアあたり約 2 倍になりました。結果の値は変わりません。

### 3. 遅い回線を避けて位置データを配る

kuro から wasat と gyh へは約 1.4 MB/s しか出ません。anna へは速く、ワーカー同士の間はさらに速い区間があります。そこで、サーバーは位置データをまず最も速いノード(今回は anna)に送ります。遅いノードは、そのノードから受け取ります。どのノードが速いかは、実際に転送した速さから自動で決めます。

また、位置データは byte を並べ替えてから zstd で圧縮して送ります。ビット単位で元に戻るので、結果は変わりません。

### 4. ノードの速さに合わせて割り当てる

ノードごとに、1 タスクの処理時間の移動平均を持ちます。速いノードに多く、遅いノードには少なく割り当てます。ステップの最後の数タスクは、遅いノードに渡しません。遅いノードが最後まで残ると、全体がそれを待つことになるためです。

### 5. 状態の保存を間引く

結果が 1 つ届くたびに状態ファイルを書き直していたため、1 ジョブあたりに約 157 ms の固定の遅れがありました。保存を 300 ms に 1 回までに制限し、約 1.5 ms になりました。

### 6. 終わったジョブを消す(`ForgetJob`)

測定を続けていると、実行が進むほど遅くなる現象が出ました。原因は、終わったジョブの結果をサーバーが消さず、状態ファイル(`state.bin`)が育ち続けることでした。180 ステップほどで **288 MB** になり、その全体を保存し続けていました。

`ForgetJob` を追加し、`map*` が結果を受け取った後にジョブを消すようにしました。修正後は `state.bin` が数十バイトのままで、実行を重ねても速さが落ちません。

### 7. ネイティブカーネル

ワーカーに AVX2 の力計算(`nbody_force`)を内蔵しました。WASM より速く、WASM の結果とビット単位で一致します。AVX2 を持たないノード(gyh)では、同じ結果になる素朴な計算に切り替わります。

| カーネル | ブロック数 408 のときの 1 ステップ(中央値) |
|---|---|
| WASM | 約 574 ms |
| ネイティブ | 約 449 ms |

## 自動チューニングの結果

次の 4 つは、利用者が何も指定しなくても決まります。

| 項目 | 自動で決めるもの |
|---|---|
| ブロック数 | `8 × スロット数` の 0.5〜2.25 倍の 4 通りを実測し、いちばん速いものを使う。24 ステップごとに測り直す |
| ネイティブか WASM か | AVX2 を持つノードのスロットが 80% 以上ならネイティブ |
| 割り当て | 計算時間に加えて、結果が返るまでの往復時間も見る |
| 位置データの転送待ち | 速いノードの実測速度から 1〜6 秒を決める |

3 台(gyh・wasat・anna)で、ブロック数を自動にして 40〜60 ステップ測った結果です。

| 回 | 1 ステップ(中央値) | 備考 |
|---|---|---|
| 再起動後の 2 回目 | 365 ms | |
| 再起動後の 3 回目 | 366 ms | |
| 別の連続した 2 回 | 396 ms と 406 ms | p90 は 432 ms と 475 ms、最大は約 650 ms |

procyon をトンネルで加えた 4 台では、中央値が 394〜410 ms、最大は約 1.0〜1.1 秒でした。

## 効かなかったこと、うまくいかなかったこと

### ブロック数は大きければ良いわけではない

WASM・3 台で、ブロック数だけを変えた結果です(同じ日の別々の回で、回ごとの差も大きい点に注意してください)。

| ブロック数 | 1 ステップ(中央値) |
|---|---|
| 204 | 約 1,500 ms |
| 300 | 約 600 ms |
| 408 | 約 570〜950 ms |
| 612 | 約 890〜990 ms |
| 816 | 約 700〜910 ms |

少なすぎると、最後に遅いノードが残って全体が待たされます。多すぎると、タスクごとの固定費が積み上がります。最適な値はクラスタの構成で変わるので、自動で選ぶ仕組み(`BlockTuner`)を入れました。

### 先読みタスク数を変えても変わらなかった

1 スロットあたりの先読み(queue depth)を 1、3、6 と変えましたが、効果がありませんでした。

### procyon は速くならなかった

procyon は kuro と同じネットワークに入っておらず、UDP が直接届きません。2 つの方法を試しました。

| 方法 | 結果 |
|---|---|
| `--relay`(n0 の中継) | 接続はできたが、N=16,384 で 1 ステップ約 15.8 秒。使えない |
| ssh トンネル(UDP を TCP に載せる) | 接続でき、procyon 単独では N=16,384 で 335 ms、N=65,536 で 2.4 秒/ステップ |

ssh トンネルで 3 台に加えると、自動チューニングの導入前は逆に遅くなりました(408 ブロックで 751 ms が 1,317 ms)。TCP の順番待ち(head-of-line blocking)で、結果の返送が遅れるためです。自動チューニングの導入後は、procyon を加えても加えなくても、約 370〜410 ms で変わりませんでした。つまり、害はなくなりましたが、得もありません。

procyon を使う手順は [PROTOCOL.md](PROTOCOL.md) の §13 にあります。

## 残っている問題

- **再起動直後の最初の実行が遅い:** クライアントを再起動した直後の最初の実行は、1 ステップ 1.3 秒前後でした。wasat と anna の間が tailscale の中継を通るためとみています。2 回目以降は約 400 ms に下がりました。コードでは直していません。
- **ときどき 1 秒を超えるステップがある:** 原因は特定できていません。anna を他の利用者と共有していることも影響していると考えられます。
- **anna の 1 コアあたりの速さ:** 約 185M 相互作用/秒で、kuro の約 690M/秒より遅く、タスクごとの固定費も約 16 ms ありました。
- **ビット一致の確認:** WASM 408 ブロックとネイティブ 408 ブロックの測定では、1 スレッドの結果と一致することを確認しました。そのあとの自動チューニングの測定は、時間がかかるため `NBODY_VERIFY=0` で確認を省いています。
- **測定の回数:** 1 台のマシンを共有している環境で、同じ日に行った測定です。回ごとの差が大きいので、数十 ms の違いは誤差の範囲です。

## 再現するには

3 台以上のワーカーをつないだサーバーで、次を実行します。

```sh
# 自動チューニング(ブロック数 0 = 自動、結果の照合は省略)
NBODY_VERIFY=0 cargo run --release -p opencompute-compute-api --example nbody_batch -- 65536 40 0

# ブロック数を固定して、カーネルも指定する
NBODY_NATIVE=1 cargo run --release -p opencompute-compute-api --example nbody_batch -- 65536 40 408

# 1 スレッドの結果と照合する(長い時間がかかります)
cargo run --release -p opencompute-compute-api --example nbody_batch -- 65536 10 408
```

| 環境変数 | 意味 |
|---|---|
| `NBODY_NATIVE=1` / `0` | ネイティブ / WASM を指定する。未指定なら自動 |
| `NBODY_VERIFY=0` | 1 スレッドの計算との照合を省く |

各ノードの測った 1 タスクあたりの時間は、`opencompute-server nodes` の `MS/TASK` 列で見られます。
